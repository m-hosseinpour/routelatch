# معماری و امنیت پیشنهادی

طرح ۲۰۲۶-۱۱-۱۷ — تصمیم‌های محصول در [نیازمندی‌ها](requirements.md) مرجع‌اند.

## ۱. مرز مسئولیت‌ها

```text
CLI / منوی ساده / GUI آینده
            │ مدیریت محلیِ محافظت‌شده
            ▼
سرویس Go ── قوانین و حالت ── pool و probe ── پیشنهادها و شواهد
    │
    ├── HTTP/CONNECT و SOCKS5 با کتابخانه‌های آماده
    │       └── ثبت اتصال: مقصد، مسیر، نسخهٔ سیاست، لغو/بستن
    │
    ├── مقصد مستقیم ── dialer مستقیم و DNS سیستم ── شبکه
    └── مقصد pool ── adapter هستهٔ رسمی Xray ── خروجی منتخب ── مقصد
```

این طرح از `D05` پیروی می‌کند ولی اتصال فنی adapter هنوز دروازهٔ آزمون دارد.
حفظ مسیر مستقیم بدون وابستگی به سلامت pool ضروری است (`D11`). panic یا crash خود
فرایند Go همچنان می‌تواند listener را متوقف کند؛ مدیریت سرویس جای تضمین شکست‌ناپذیری نیست.

کد اختصاصی برای سیاست، وضعیت، پیشنهادها، انتخاب خروجی و ثبت/قطع اتصال است؛
VLESS/Trojan/XHTTP، رمزنگاری و parsing پروتکل HTTP/SOCKS نباید از صفر نوشته شوند.
یک مالک سرویس، وضعیت پایدار را تغییر می‌دهد؛ CLI فایل‌ها را هم‌زمان بازنویسی نمی‌کند.

## ۲. اتصال کتابخانه‌ای و دروازهٔ Xray

سورس `v26.11.9` رابط `core.Dial` و dispatcher دارد و feedback خطای outbound را
از context می‌گیرد؛ اما `core.Dial` می‌تواند پیش از برقراری واقعی مقصد برگردد.
نبودن error در آن لحظه، اثبات سلامت اتصال نیست. [شواهد E03–E05](research.md)

در `T1` باید اتصال واقعی، error feedback، first-byte/timeout، لغو و teardown تحت
transportهای نمونه بررسی شوند. موفقیت CONNECT/SOCKS و گزارش خطای آن‌ها نباید
بر پایهٔ یک فرض نادرست از semantics موتور باشد.

زمان ارسال CONNECT `2xx` و SOCKS5 `0x00` دروازهٔ صریح است: باید تشکیل اتصال مقصد
یا راه جایگزینِ سازگار و آزموده اثبات شود. بعضی transportها ارسال اولیه می‌خواهند؛
نمی‌توان بی‌بررسی تا first-byte منتظر ماند یا برگشت Dial را readiness دانست. اگر API
این مرز را قابل اثبات نکند، معماری اتصال باز می‌شود؛ تضمین با یک reply زودهنگام
و خطای متنی بعدی پنهانی ضعیف نشود.

پیشنهاد: استفاده از adapter باریک و نسخهٔ pinned؛ مسیر انتخاب‌شده به tag مشخص
موتور وصل شود. هسته هیچ fallback به direct برای مسیر pool نداشته باشد. اگر از
balancer هسته استفاده شد، fallback صریح reject/blackhole لازم است؛ اگر انتخاب در
Go انجام شد، نبود خروجی سالم قبل از dispatch به خطای `pool unavailable` برسد.

مدیریت اتصال‌های کاربر در frontend خودمان است. هر اتصال/تلاش در حال برقراری نسخهٔ
سیاست و مسیر دارد. تغییر حالت پذیرش/تصمیم جدید را هماهنگ می‌کند، اتصال‌های متعارض
را cancel/close می‌کند و فقط بعد از اعمال نتیجه موفقیت اعلام می‌کند. warm HTTP
transport pools و کانال‌های hijacked هم بخشی از این ثبت‌اند؛ صرف تغییر جدول کافی نیست.

Go/Xray تعدادی وضعیت process-global دارد. ایجاد چند core برای probe و سرویس در
همان فرایند، بی‌بررسی مجاز نیست. ترجیح probe در core فعال با tag صریح یا helper
ایزوله از همان بسته است؛ روش نهایی بعد از `T1`، بدون الزام نصب دستی موتور.

## ۳. سیاست مسیر و DNS

- یک مدل مقصد نوع‌دار و یک فهرست مشترک (`D10`).
- استثنای localhost/LAN پیش از سیاست عمومی اعمال شود (`D17`). مشخص‌بودن آدرس
  واقعی، دامنهٔ local و جلوگیری از DNS rebinding/حلقه در `T2` آزمون و تعریف شود.
- در targeted فقط تطبیق صریح مقصد pool است؛ IP نامشخص خارج از فهرست direct است.
- پیشنهاد: بدون lookup اضافه صرفاً برای گسترش دامنه به تمام IPهای CDN. قواعد IP
  باید semantics روشن داشته باشند؛ تطبیق hostname با IPهای resolveشده مسئلهٔ جداست.
- remote destination hostname تا خروجی حفظ شود؛ صرف نصب یک SOCKS library کافی نیست:
  بعضی کتابخانه‌ها پیش از dial سفارشی local resolve می‌کنند. [E08](research.md)
- bootstrap hostname سرور خروجی ممکن است DNS زیرین نیاز داشته باشد؛ با DNS مقصد
  پروکسی‌شده یکسان نیست و باید صریح توضیح داده شود.
- IPv4/IPv6 مقصد، IP literal و IPv4-mapped IPv6 یکسان‌سازی و آزمون شوند؛ عدم پشتیبانی
  یک مسیر نباید bypass مستقیم ایجاد کند.

نسخهٔ اول DNS سیستم یا firewall را تغییر نمی‌دهد. sniffing به‌عنوان پایهٔ تضمین
قانون دامنه انتخاب نشده است. ECH و CDN مشترک این تضمین را محدود می‌کنند.

## ۴. pool و سلامت

مدل پیشنهادی: منبع → رکورد کانفیگ canonical → وضعیت اعتبارسنجی/اعتماد → شواهد
سلامت → انتخاب خروجی. ترتیب ورودی کاربر حفظ شود ولی تاریخچهٔ کیفیت جدا نگهداری شود.

- حذف duplicate بر مبنای تنظیم اتصال، نه فقط host:port یا عنوان.
- منبع، عنوان و اشتراک‌های مالک رکورد جدا از شناسهٔ اتصال؛ یک لینک مشترک در دو
  اشتراک با refresh یکی بی‌دلیل حذف نشود.
- invalid/unsupported/quarantined/unknown/healthy/cooling متمایز باشند.
- اولین تست سلامت از tag همان خروجی و مستقل از فهرست مقصدهای کاربر عبور کند.
- سنجش latency، موفقیت و failure-rate؛ حفظ خروجی سالم فعلی، hysteresis و cooldown.
- سنجش‌ها محدود و نمونه‌گیری گردشی باشند؛ آستانه‌ها بعد از داده/آزمون تعیین شوند،
  نه کپی عددهای اسکیل یا ادعای «reset یک‌سوم درخواست‌ها».
- خرابی مقصد با خرابی کل خروجی یکسان نیست؛ یک پاسخ بد سایت pool را نابود نکند.
- کانفیگ تازه پیش از استفادهٔ کاربر اعتبارسنجی و طبق سیاست سلامت آماده شود.
- حذف/تغییر رکورد، اتصال جدید را متوقف کند؛ رفتار اتصال زنده هنگام refresh و rotate
  در `T2` روشن شود. برای تغییر عادی انتخاب، اتصال سالم قبلی ترجیحاً drain شود.

به‌روزرسانی اشتراک باید محدودیت اندازه/زمان/redirect، parsing بدون اجرای داده،
اعتبارسنجی هر رکورد و commit اتمیک داشته باشد. failure، payload نامعتبر یا صفر خروجی
قابل استفاده، pool سالم قبلی را به‌طور پیش‌فرض پاک نکند. خالی‌کردن واقعی منبع یک
عمل صریح یا سیاست روشن است، نه نتیجهٔ یک خطای HTML.

`libXray` نامزد reuse برای parsing است، نه وابستگی قطعی. API stability تضمین نمی‌کند،
ممکن است invalidهای فردی را حذف کند و نتیجهٔ per-node ندهد. برای قرنطینه و گزارش
دقیق باید توانش در `T1/T2` بررسی شود. raw config فقط به‌عنوان دادهٔ خروجی مجاز و
پس از sanitization باشد؛ root `routing`/`dns`/`env`/`api`/inbounds، script، فایل‌های
محلی یا outbound dependency ناشناس از اشتراک اجرا نشوند. حفظ XHTTP extra مجوز
اجرای arbitrary config نیست. [E09](research.md)

## ۵. پیشنهادها و حریم خصوصی

فقط خطاهای eligible مستقیم وارد صف شوند. برای هر مقصد cooldown و سقف هم‌زمانی/
تعداد لازم است. صف، دلیل، نوع آزمایش، نتیجه و تازگی را نشان می‌دهد، نه حکم «مسدود است».

diagnostic اتصال مستقل است و درخواست اصلی را بازپخش نمی‌کند. TLS probe برای hostname
از اعتبارسنجی کامل استفاده کند. برای IP بدون نام، TCP success با برچسب همان مرحله
ثبت شود؛ خاموش‌کردن verification برای ساخت پیشنهاد ممنوع است. UDP بعداً semantics
جدا دارد؛ «دیتاگرام بی‌پاسخ» به‌خودی‌خود شکست مسیر نیست.

evidence فقط مقصد/پورت و اطلاعات لازم را نگه دارد، نه URL کامل، query، headers، body،
کوکی یا token. retention محدود و قابل پاک‌کردن صریح باشد؛ تغییر mode، cancel، EOF
عادی، auth/rate-limit سایت یا TLS نامعتبر شواهد اثبات نیاز به pool نیستند.

پیشنهادهای ردشده و درخواست بررسی مجدد لازم‌اند؛ حذف قانون یا بازبررسی مستقیم فقط
با تصمیم کاربر. خاموشی تشخیص، آزمایش‌های صف‌شده را نیز لغو کند.

## ۶. امنیت محلی و ورودی‌ها

| تهدید | کنترل پیشنهادی | محدودیت |
| --- | --- | --- |
| استفادهٔ کاربر محلی دیگر از pool | loopback و هشدار حالت بدون رمز | طبق D14 احراز هویت traffic نداریم؛ این ریسک باقی است |
| تغییر mode/rules توسط کاربر دیگر یا صفحهٔ وب | مدیریت در Unix socket خصوصی روی لینوکس؛ مجوز/peer identity، بدون HTTP مدیریتی باز | فرایند هم‌حساب یا root مرز امنیتی جدا محسوب نمی‌شود |
| موتور/API داخلی بی‌احراز هویت | API عمومی موتور فعال نشود مگر نیاز واقعی؛ اگر لازم شد socket خصوصی، نه loopback باز | loopback API پنهان «امن» نیست |
| خروجی عمومی مخرب | no MITM، TLS مقصد، برچسب اعتماد و قرنطینهٔ verification خاموش | خروجی metadata را می‌بیند؛ HTTP مقصد می‌تواند plaintext باشد |
| subscription یا share link مخرب | schema/sanitization، عدم پذیرش root config، محدودیت اندازه/منبع، پیام خطای redacted | config builder sandbox نیست و ممکن است فایل/وضعیت process را تغییر دهد |
| secret روی دیسک و terminal | پوشهٔ خصوصی، فایل 0600، atomic write، محافظت symlink، redaction و حذف control/escape از عنوان‌ها | در ویندوز chmod جای ACL نیست؛ باید جدا طراحی شود |
| فرایند یا فایل نامرتبط | singleton/ownership؛ نصب و import محدود، no broad kill/delete | هیچ مسیر قدیمی بی‌مجوز بازنویسی نشود |
| loop به listener/مدیریت | جلوگیری از proxy-to-self و deny مقصد مدیریت؛ استثنای محلی کنترل‌شده | LAN مستقیم به معنی اجازهٔ دسترسی به control socket نیست |

فعال‌سازی استثنای TLS ناامن باید محدود، قابل لغو و در وضعیت قابل مشاهده باشد؛
انتخاب واحد رضایت کانفیگ/منبع قبل از ساخت در `T2` با کاربر بسته شود.

## ۷. سرویس و استفاده

foreground command مبناست؛ systemd user unit روی لینوکس افزونهٔ مدیریت lifecycle است،
نه وابستگی policy. hardening بدون شکستن direct egress و با کمترین مجوز لازم طراحی
شود؛ root یا TUN در نسخهٔ اول لازم نیست.

launcher تنظیمات را فقط در فرایند فرزند تزریق کند؛ محیط قبلی بدون تصمیم روشن مسیر را
عوض نکند. توقف/عدم سلامت listener مجوز اجرای مستقیم برنامه نیست. در **فرزندهای
اجراشده توسط launcher**، `NO_PROXY` ارث‌رسیده نباید قانون تأییدشده را دور بزند؛
استثناهای محلی محدود و قابل توضیح باشند. تنظیم proxy/bypass یا محیط برنامه‌ای که
مستقلاً اجرا شده خارج از کنترل ماست، همان‌طور که DNS مستقل مصرف‌کننده خارج از
listener است. launcher نمی‌تواند برنامهٔ بی‌اعتنا به env/proxy را اجباراً capture کند.

تنظیم پروکسی دسکتاپ opt-in است. مقدار قبلی ذخیره شود و restore فقط تنظیمی را
بازگرداند که هنوز تحت مالکیت RouteLatch است؛ تغییر جدید کاربر overwrite نشود.
crash می‌تواند اشارهٔ دسکتاپ به listener مرده باقی بگذارد؛ فرمان بازیابی offline لازم
است. GNOME/KDE و سایر محیط‌ها ماتریس توان جدا دارند؛ unsupported یعنی پیام روشن،
نه ادعای «پروکسی کل سیستم».

## ۸. مراحل بعدی

TUN و UDP با قواعد مشابه اما capture/DNS/privilege/teardown متفاوت‌اند. Xray در
نسخهٔ بررسی‌شده زیرساخت TUN دارد؛ اپ Android همچنان `VpnService` بومی می‌خواهد.
نباید فرض کنیم stock TUN به registry اتصال frontend نسخهٔ اول متصل می‌شود؛ حفظ
رفتار `D13` روی TUN دروازهٔ فنی جدید دارد.

GUI مصرف‌کنندهٔ همان management interface باشد. برای Android Go runtime مشترک
و build artifact واحد در هر فرایند لازم است؛ `libXray` و کتابخانهٔ Go مستقل نباید
به‌صورت دو runtime جدا داخل یک فرایند بار شوند.
